# USV Replay Lab 项目设计

**要解决的问题是岸站在失去艇载心跳后仍显示在线。** 开发者需要在没有实艇的情况下把这个问题复现出来，核对告警时间，并保证下次修改通信代码时同一个问题不会复发。

最初使用者是维护无人艇岸站、艇载设备驱动或通信库的 C++ 开发者，以及在实验室学习 UDP、TCP 和串口的团队。团队现有训练从 Ubuntu 和 C++ 基础进入通信、串口和动态库，适合从回放核心起步，把后续每种通信方式逐步接成适配器。Qt 界面可通过接入示例使用结果，命令行核心保持标准 C++。

## 首个用例

在养护巡检或水质监测等应用中，艇载设备周期向岸站发送心跳。测试人员要区分三个可观察结果：

| 场景 | 预期 |
| --- | --- |
| 心跳正常 | 岸站保持在线，无超时事件。 |
| 从 600 毫秒起暂时收不到心跳 | 500 毫秒收到最后一条，300 毫秒后出现超时。 |
| 心跳在 1100 毫秒恢复 | 状态恢复在线，报告包含恢复事件。 |

这是一个从通信开发需求提取的**可复现问题模型**。本地实验已经证明可以检测教学版漏报。生态价值仍需通过实际使用者提供的故障或接入案例来验证。

使用者的目标流程：

1. 把可分享的输入、故障窗口和预期放在同一用例目录。先用项目自带的合成输入跑通。
2. 用离线时钟回放并检查预期与观测结果。保存报告、工具版本和输入哈希。
3. 在修复通信逻辑后原样重跑。测试代码将结果接入构建，失败时指出第一个不同的事件和时间。
4. 将可公开的最小复现用例随 Issue 或 PR 共享。经维护者确认可复用后，加入项目的回归集合。

## 架构与取舍

~~~mermaid
flowchart LR
    A["合成心跳 CSV"] --> V["输入校验"]
    B[".case 场景和期望"] --> V
    V --> F["按时刻筛除丢失事件"]
    F --> T["虚拟时钟推进"]
    T --> M["被测链路监视器"]
    M --> C["比较观测与期望"]
    B --> C
    C --> R["JSON 报告和进程退出码"]
~~~

| 模块 | 本地 0.2.0 | 演进边界 |
| --- | --- | --- |
| 输入 | 两列心跳 CSV，六字段场景 v1 | 有复用需求时添加协议帧格式和可移植复现包，旧格式保留。 |
| 故障模型 | 固定左闭右开丢失窗口 | 扩展到应用消息重复、延迟和设备重启。若需要随机模型，记录算法版本和种子。 |
| 时间 | 单线程、整数毫秒、事件顺序稳定，回放到明确终点 | 网络适配器单独测量实际时钟，保留离线确定性用例。 |
| 被测对象 | 参考监视器和故意漏报对照 | 通过小接口或适配示例对接使用者已有监视器，把回放和业务状态机拆开。 |
| 输出 | 比对完整事件序列，JSON 和退出码 | 根据首个接入方的需求增加首个差异、JUnit 或版本元数据。 |
| 通信 | `usv_comm` UDP/TCP 动态库，四个客户端/服务端示例；TCP 4 字节长度分帧、二进制/空帧、限时 I/O | 先把 UDP 设备消息转为回放事件。串口、DNS、IPv6、TLS 与异步模型按真实接入需求设计。 |
| 构建 | C++17、CMake 静态回放核心与动态通信库；安装包、独立消费工程及 CTest | 本地 Windows/MSVC 与 WSL Ubuntu 26.04.1/GCC 验证通过。Ubuntu 24.04/Windows CI 配置已完成，远程结果以仓库 Actions 的实际运行记录为准。 |

文件语法、时序优先级及错误处理以[输入与报告契约](formats.md)为准。逻辑层与文件读写分别实现，测试从命令行验证真实入口。离线测试可以要求 0 毫秒逻辑误差。涉及套接字、串口和系统调度的测试另设容差，实艇验收还需观测无线、供电、串口电气层与设备时钟。

通信模块的 [API 与线格式](communication.md)单独约定。公开接口位于 `include/usv_comm/`，实现位于 `src/comm/`；消费工程通过安装包链接共享库，不引用实现源码。当前离线回放与实际套接字测试分别通过，[通信验证记录](communication_validation.md)列出证据；网络到事件的记录和转换仍待实现。这样既能使用精确虚拟时间检查状态逻辑，也能用真实本机 I/O 检查分帧、错误与资源释放。

## 与现有工具的关系

| 工具 | 已有能力 | 本项目适合承担的部分 |
| --- | --- | --- |
| Linux `tc netem` | 网络层延时、丢失、重复、损坏、乱序，可用随机种子。[手册](https://man7.org/linux/man-pages/man8/tc-netem.8.html) | 在应用层表达心跳缺失、坏帧处理、恢复和自动断言。网络层实验可单独配合使用。 |
| `socat` | TCP、UDP、串口和伪终端等端点的双向转发。[上游文档](https://www.dest-unreach.org/socat/doc/socat.html) | 为转发端点提供可复用的虚拟设备行为、测试数据和预期报告。 |
| ROS 2 `rosbag2` | ROS 2 消息录制与回放，支持回放控制。[官方仓库](https://github.com/ros2/rosbag2) | 服务基于原生 C++/Qt 的设备协议与字节流解析器。若已有 ROS 日志，可按需增加转换。 |
| MOOS-IvP 日志工具 | `alogcheck` 等工具可检查海洋机器人日志并支持自动化测试。[官方工具文档](https://oceanai.mit.edu/ivpman/pmwiki/pmwiki.php?n=IvPTools.ToolsIntro) | 给不用 MOOS 的项目提供独立的最小复现包和设备通信断言。 |

可以验证的差异化是：让独立团队把通信故障用例随 Issue 共享、在修复前后运行，并保留为 CI 回归。应优先验证这条流程在实际项目里是否省力，再决定扩展哪些传输方式。

## 最终交付

目标是一个带公开文档和版本发布的工具仓库，交付可独立构建的 C++ 核心、CLI 与通信动态库、版本化场景和合成数据、至少一个参考设备适配器、自动验收流程，以及可核验的实际接入案例。当前已交付离线核心、UDP/TCP 共享库与本机软件验证；监视器适配、设备事件录制和串口软件端仍按[路线图](roadmap.md)推进。当前尚无外部采用或实艇验证记录。

对使用者而言，结果是能用一条命令回答“此版本在这个通信故障下是否按时告警、是否正确恢复”。对维护者而言，结果是能够引用同一份输入和测试报告，缩短故障复现和回归检查的来回沟通。是否改善真实开发流程，需要使用方用实际案例验证。
